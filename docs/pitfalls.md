# 实际问题与可复用经验

以下记录按“现象 → 调查或原因 → 修正 → 可复用结论”组织。数值和地址属于具体案例；
迁移到新游戏时复用调查方法，并重新验证格式、资源占用和时序。

## 字形基线与裁切

Pure 的对话窗口会裁到首个扫描行。把新增中文字形上移一像素会让首行缺笔。
沿用的 Cure 菜单字占 y=0..10，其他新增字占 y=1..11，混用时“戏”看起来比“游戏”的“游”低。
P05 沿用 P04 的处理：保留顶部空行，沿用菜单字下移一像素；不是把其他字也移入裁切区域。

居中检查应使用**可见墨迹包围盒**。固定字符格居中不一定是视觉居中。Pure 四项菜单最终墨迹中心均为 x=80。

**可复用结论：** 分别检查字符格、可见墨迹和窗口裁切边界；以实际截图验证基线与居中，不能直接沿用案例像素偏移。

## 双层图块与色块

原提示文字可能由两个平面和不同透明色拼合。只把 tile 当作连续画布重画，会留下蓝底或缺笔。
标题提示需要同时处理两层 tilemap；圈 A 保留原像素形状，两侧可见空隙统一为 5px。
重新安排资源时还需控制 tile 去重与数量，避免改变资源加载时长。

**可复用结论：** 同时追踪组成目标文字的图层、透明色与资源加载过程；修改前确认最终画面由哪些资源合成。

## 空闲图块、调色板不能靠猜

P04 实装署名过程中，图块 480..499 会覆盖标题下部的文字缓冲；调色板 15 会影响菜单文字颜色。
最后使用标题资源与文字缓冲之外的 352..371 和当时未使用的滚动层调色板 3。
这些是本场景的实测选择，不能原样用于其他游戏。

**可复用结论：** 资源是否空闲要覆盖场景切换和后续写入来判断，不能只看单帧；图块和调色板编号属于项目事实。

## 预绘制不是显示完成

原版先把文字准备到显存，再播放滑入动画。署名挂在字体调用处会在第 3 帧先出现。
P05 移到原版菜单就绪处理，按脚本地址和标题文本上下文限定，不加固定帧延迟。
冷启动按 A 后，历史 Med / Native 观测分别在第 25 / 28 帧显示署名，并不需要让两个核心的绝对帧号相同。

**可复用结论：** 先区分准备数据和显示就绪的事件，再选择钩子；固定延迟只能掩盖尚未确认的触发条件。

## 时序与声音

为追平一个模拟器而随意改变 ROM 等待量，可能破坏另一核心或掌机上的时机。
《Cure.》曾出现不同模拟器与 RG35XX 对开场音画的表现不一致，必须分别留证。

录制时音频需连续取出并完全消费。Pure 的 Beetle 核心 AV 元数据报告 60.25fps，
但实际产生的 PCM 与 515×199 栅格时钟对应；直接按 60.25fps 编码约 85 秒会领先声音约 0.42 秒。
当前录制脚本使用 `6144000/102485` 的视频时间基，保留原 PCM；结果以样本数与帧数交叉核对。

**可复用结论：** 分别保存各核心与硬件的观测，核对视频帧数、PCM 样本数和实际时间基；案例里的常量不能直接迁移。

## 脚本触发不等于可见

P05 的两个核心都能到达相同开场文本入口，且分别与原版时点一致。
但是这次 Native 录制中两页黑底叙述为黑屏，Beetle 正常。根因尚未确定。
不能把路径和时序检查通过写成“全部画面正确”，也不能在没有对照证据时把失败归因于 ROM。

**可复用结论：** 将执行路径、显示可见性和时序作为独立检查项；失败保留待查，不因另一项通过而忽略。
